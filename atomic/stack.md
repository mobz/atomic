# Stack: Pipeline cleanup and hardening
As a developer using atomic, I want the docs, CLI, and /at:* commands to match how the pipeline actually works — shared format context, accurate entry states and behaviours, safe failure paths, and clear rules for how the stack is committed — so that each command can be followed exactly without hitting stale or contradictory instructions.

## Proposal: Steer `/at:propose` to decide whether new work belongs in the current stack or a separate one
Deferred from spec: split off from the `/at:propose` → `/at:propose` rename (a behaviour change, not a rename). When the user brings new work, `/at:propose` today only asks **Extend** / **Fresh** about the one active stack. Add explicit steering before drafting: compare the work against the active stack's user story — if a proposal is in scope of that story (the story's own test: "specific enough to decide whether a proposal is in or out of scope"), fold it in (extend, placed by dependency/urgency); if it serves a different persona or goal, or could ship and be reviewed independently of the active stack, it is a separate stack. State the call and the reason, and let the user override, as a gate (e.g. **Fold** — add to the current stack / **Separate** — start a new stack). Weigh parallelism (the README's purpose): separate stacks can run in parallel, so prefer separate when the work has no dependency on the active stack.

Dependency: a separate stack means writing `atomic/stacks/<name>.md` (or replacing the active stack), which has no committed path yet — see "Decide how planning edits other than a plain append are committed" and `atomic/stacks/stack-awareness.md`. Until that lands, **Separate** can only draft the new stack and hand off for a reviewed hand commit, or this proposal waits for it. Decide ordering during spec. Update `pipeline-propose.md` and the command's step 1.

## Proposal: Decide how planning edits other than a plain append are committed — rewriting, reordering, removing, and moving proposals between `atomic/stack.md` and `atomic/stacks/*`
Deferred from spec: split off from wiring `atomic stack-add` into `/at:propose`. `atomic stack-add` only appends one block to the end of `atomic/stack.md`; every other planning edit has no committed path. A `/at:propose` "start fresh" or "replace" rewrite in state `none` currently rides along with the first spec's commit (via `git add -A`), mixing planning into that commit; moving a proposal to a parked stack (e.g. the critic spike to `atomic/stacks/research.md`) needed a one-off hand `Propose:` commit. Options: an `atomic stack-replace` CLI that commits a new file as `Propose: <stack name>` (state `none` only); a general `atomic plan-commit` that commits only `atomic/stack.md` and `atomic/stacks/*` from a reviewed working-tree change (state `none` only, since mid-apply the stack also holds the pop and deferrals); or `stack-move`/`stack-remove` commands built like `stack-add` (from HEAD in a temporary index). Keep the review step: show the exact change and get approval before committing.

## Proposal: Decide how a repo gets its first `atomic/stack.md` — probably create it when first needed, without being too fussy
Deferred from spec: while specifying `/at:init`, found that nothing creates `atomic/stack.md` until `/at:propose` runs. `atomic stack-add` refuses when the stack is not in HEAD, and `.claude/docs/stack-context.md` says a deferral with no stack should "create it with just the Proposal block", contradicting the mandatory `Stack:` header (also in `pipeline-apply.md` "scope enforcement — stack.md does not exist"). Simplest is likely: whatever first needs a stack (a deferral, `atomic stack-add`, `/at:propose`) creates it with a minimal header such as `# Stack: Backlog`, rather than `atomic init` scaffolding one up front. Decide, then make `stack-add` and the stack rules agree.

## Proposal: Make `bin/atomic` reject unknown flags instead of silently dropping them
Deferred from spec: while specifying consistent `--json` errors, found that the argument loop in `bin/atomic` drops every `-`-prefixed argument other than `--json` (`-*) ;;`). A typo like `--jsno` is ignored, and a positional argument that starts with `-` (e.g. a `stack-add` intent) is lost. Options: error on unknown flags via `die`; support `--` to end flag parsing.

## Proposal: Write the spec to disk before the first human interaction in `/at:spec`, then offer the post-write choices plus "Or tell me what to change"
Deferred from spec: while specifying consistent `--json` errors, the user noted that the spec flow asks for confirmation (step 4 "Summarise back", in practice a **Write** choice) before anything is on disk. Instead, once clarify has enough to go on, write `atomic/spec.md` (and do the stack pop, split-offs, and deferrals) straight away, then hand back with choices like those after a spec is written — e.g. **Apply** — implement this spec now / Or tell me what to change. Changes are edits to the written spec, so the user reviews the real file rather than a summary of it. Overlaps with "Remove the "Summarise back" confirmation step from `/at:spec`" in `atomic/stacks/stack-awareness.md` (move or drop that one when this is done) and with the interaction-pattern proposal (whose candidate list names spec step 4's **Write**). Consider what "tell me what to change" means for the stack: a spec rewritten from scratch may need the pop undone.

## Proposal: Make `/at:spec` write `atomic/spec.md` before popping the stack, so an interrupted spec can't silently skip a proposal
Noticed by the user: step 6 updates the stack "in the same step as writing the spec" but gives no order, and in practice the pop has been written first. If Claude is terminated between the two writes, the state is `none` with the top proposal already gone from the working tree. The next `/at:spec` surfaces the *second* proposal, and the first only survives as an uncommitted diff (recoverable from git, but easy to miss and sweep into an unrelated commit).

Fix: step 5 writes `atomic/spec.md` first; step 6 pops and writes deferrals only after the spec is on disk. The worst interrupted state then becomes "spec exists, proposal still on the stack" — visible (`atomic status` says `proposed`) and recoverable by re-doing the pop. Update the `pipeline-spec.md` scenario "spec written from stack proposal, proposal popped" (today it says "written together") and `stack-context.md` if it implies order.

Option to decide during spec: an `atomic stack-pop` CLI that removes the top block and refuses unless `atomic/spec.md` exists, so the order is enforced by the CLI rather than by prompt wording. It would also make the pop exact (today it is done by hand-editing).

## Proposal: Let stage-end hand-offs offer the next command as a gate verb (e.g. **Spec** — start `/at:spec` now), keeping `Next:` lines for wrong-state exits
Noticed by the user after the interaction pattern shipped: at the end of a stage (merge done, spec written, stack written, init done) the commands end with `Next: /at:<command>`, so the user must type the slash command — unlike `/at:apply`, where **Approve** chains into `/at:merge` itself. Option: make stage-end hand-backs a gate whose verbs run the next command in the same session, with "Or tell me what to change" last; keep `Next:` for wrong-state exits, where nothing should run.

Verbs under current terminology:
- `/at:merge` done → **Spec** — spec the top proposal (`/at:spec`) / **Propose** — propose new work as a stack (`/at:propose`)
- `/at:spec` spec written → **Apply** — implement it (`/at:apply`)
- `/at:propose` stack written → **Spec** — spec the top proposal
- `/at:init` done → **Spec** / **Propose**, as after merge

Weigh against context growth: chaining stages in one session accumulates context, which cuts against small models and parallel stacks — consider whether the gate should note "or start it in a fresh session". Update `interaction-context.md` (handoff vs gate definitions), the five commands, their behaviours, and the manifest entry.
