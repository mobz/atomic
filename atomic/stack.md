# Stack: Pipeline cleanup and hardening
As a developer using atomic, I want the docs, CLI, and /at:* commands to match how the pipeline actually works — shared format context, accurate entry states and behaviours, safe failure paths, and clear rules for how the stack is committed — so that each command can be followed exactly without hitting stale or contradictory instructions.

## Proposal: Decide whether `atomic commit` refuses when there is no `atomic/spec.md`
Deferred from propose: split off from wiring `atomic stack-add` into `/at:stack` and CLAUDE.md (a CLI behaviour change, a separate concern). With no spec, `atomic commit` falls back to message "atomic commit" and `git add -A` — the path that sweeps stray edits (e.g. hand-edited stack additions) into vague commits. Options: refuse with an error pointing at `/at:propose` or `atomic stack-add`; or keep the fallback. Update `cli-atomic.md` "commit — no spec", help, README, and `merge.md` if it changes.

## Proposal: Decide how planning edits other than a plain append are committed — rewriting, reordering, removing, and moving proposals between `atomic/stack.md` and `atomic/stacks/*`
Deferred from propose: split off from wiring `atomic stack-add` into `/at:stack`. `atomic stack-add` only appends one block to the end of `atomic/stack.md`; every other planning edit has no committed path. A `/at:stack` "start fresh" or "replace" rewrite in state `none` currently rides along with the first spec's commit (via `git add -A`), mixing planning into that commit; moving a proposal to a parked stack (e.g. the critic spike to `atomic/stacks/research.md`) needed a one-off hand `Plan:` commit. Options: an `atomic stack-replace` CLI that commits a new file as `Plan: <stack name>` (state `none` only); a general `atomic plan-commit` that commits only `atomic/stack.md` and `atomic/stacks/*` from a reviewed working-tree change (state `none` only, since mid-apply the stack also holds the pop and deferrals); or `stack-move`/`stack-remove` commands built like `stack-add` (from HEAD in a temporary index). Keep the review step: show the exact change and get approval before committing.

## Proposal: Rename `/at:propose` to `/at:spec`, so the command is named for what it produces (`atomic/spec.md` from the top proposal)
The stack is a stack of proposals, but `/at:propose` does not create proposals; it turns one into a spec. Renaming it frees the `/at:propose` name for the command that does create them (next proposal). Pipeline becomes `stack → spec → apply → merge` until then.

Changes: move `.claude/commands/at/propose.md` to `spec.md`; update every reference meaning "turn a proposal into a spec": `apply.md`, `merge.md`, `stack.md`, `.claude/docs/stack-context.md`, `CLAUDE.md` (pipeline, rule 1, Slash Commands table), `README.md` (Pipeline table and diagram), `bin/lib/atomic-show-spec` error ("run /at:spec first"), the `bin/lib/atomic-rollback` comment, and behaviours (rename `pipeline-propose.md` to `pipeline-spec.md`; update `pipeline-apply.md`, `pipeline-merge.md`, `pipeline-stack.md`, `command-context.md`). Keep the `Deferred from propose:` source line as is, since a deferral can come out of either command. Update references in the stack files (`atomic/stack.md`, `atomic/stacks/*`) too, so queued proposals don't point at the wrong command.

No alias: `atomic init` copies commands once and repos own them afterwards, so there are no downstream consumers to keep working.

## Proposal: Rename `/at:stack` to `/at:propose`, so creating proposals — a new stack, or additions to an existing one — is "propose"
Depends on the rename above, which frees the name. The command keeps everything `/at:stack` does: elicit a user story, decompose into proposals, write a new stack (refused while a spec is active), or extend the current one via `atomic stack-add`. Reword its intro around "propose work as proposals in the stack". Pipeline becomes `propose → spec → apply → merge`.

Changes: move `.claude/commands/at/stack.md` to `propose.md`; update references in `spec.md`, `apply.md`, `CLAUDE.md` (pipeline, rule 6, Slash Commands table), `README.md`, `.claude/docs/stack-context.md`, and behaviours (rename `pipeline-stack.md` to `pipeline-propose.md`). `Deferred from propose:` now reads naturally for deferrals found during `/at:spec`; decide whether to rename it to `Deferred from spec:`. The `Plan:` commit prefix stays.

## Proposal: Decide how a repo gets its first `atomic/stack.md` — probably create it when first needed, without being too fussy
Deferred from propose: while specifying `/at:init`, found that nothing creates `atomic/stack.md` until `/at:stack` runs. `atomic stack-add` refuses when the stack is not in HEAD, and `.claude/docs/stack-context.md` says a deferral with no stack should "create it with just the Proposal block", contradicting the mandatory `Stack:` header (also in `pipeline-apply.md` "scope enforcement — stack.md does not exist"). Simplest is likely: whatever first needs a stack (a deferral, `atomic stack-add`, `/at:stack`) creates it with a minimal header such as `# Stack: Backlog`, rather than `atomic init` scaffolding one up front. Decide, then make `stack-add` and the stack rules agree.

## Proposal: Make `bin/atomic` reject unknown flags instead of silently dropping them
Deferred from propose: while specifying consistent `--json` errors, found that the argument loop in `bin/atomic` drops every `-`-prefixed argument other than `--json` (`-*) ;;`). A typo like `--jsno` is ignored, and a positional argument that starts with `-` (e.g. a `stack-add` intent) is lost. Options: error on unknown flags via `die`; support `--` to end flag parsing.

## Proposal: Write the spec to disk before the first human interaction in `/at:propose`, then offer the post-write choices plus "Or tell me what to change"
Deferred from propose: while specifying consistent `--json` errors, the user noted that the spec flow asks for confirmation (step 4 "Summarise back", in practice a **Write** choice) before anything is on disk. Instead, once clarify has enough to go on, write `atomic/spec.md` (and do the stack pop, split-offs, and deferrals) straight away, then hand back with choices like those after a spec is written — e.g. **Apply** — implement this spec now / Or tell me what to change. Changes are edits to the written spec, so the user reviews the real file rather than a summary of it. Overlaps with "Remove the "Summarise back" confirmation step from `/at:propose`" in `atomic/stacks/stack-awareness.md` (move or drop that one when this is done) and with the interaction-pattern proposal (whose candidate list names propose step 4's **Write**). Consider what "tell me what to change" means for the stack: a spec rewritten from scratch may need the pop undone.

## Proposal: Make `/at:propose` write `atomic/spec.md` before popping the stack, so an interrupted propose can't silently skip a proposal
Noticed by the user: step 6 updates the stack "in the same step as writing the spec" but gives no order, and in practice the pop has been written first. If Claude is terminated between the two writes, the state is `none` with the top proposal already gone from the working tree. The next `/at:propose` surfaces the *second* proposal, and the first only survives as an uncommitted diff (recoverable from git, but easy to miss and sweep into an unrelated commit).

Fix: step 5 writes `atomic/spec.md` first; step 6 pops and writes deferrals only after the spec is on disk. The worst interrupted state then becomes "spec exists, proposal still on the stack" — visible (`atomic status` says `proposed`) and recoverable by re-doing the pop. Update the `pipeline-propose.md` scenario "spec written from stack proposal, proposal popped" (today it says "written together") and `stack-context.md` if it implies order.

Option to decide during propose: an `atomic stack-pop` CLI that removes the top block and refuses unless `atomic/spec.md` exists, so the order is enforced by the CLI rather than by prompt wording. It would also make the pop exact (today it is done by hand-editing).
