# Stack: Pipeline cleanup and hardening
As a developer using atomic, I want the docs, CLI, and /at:* commands to match how the pipeline actually works — shared format context, accurate entry states and behaviours, safe failure paths, and clear rules for how the stack is committed — so that each command can be followed exactly without hitting stale or contradictory instructions.

## Proposal: Decide how planning edits other than a plain append are committed — rewriting, reordering, removing, and moving proposals between `atomic/stack.md` and `atomic/stacks/*`
Deferred from propose: split off from wiring `atomic stack-add` into `/at:stack`. `atomic stack-add` only appends one block to the end of `atomic/stack.md`; every other planning edit has no committed path. A `/at:stack` "start fresh" or "replace" rewrite in state `none` currently rides along with the first spec's commit (via `git add -A`), mixing planning into that commit; moving a proposal to a parked stack (e.g. the critic spike to `atomic/stacks/research.md`) needed a one-off hand `Plan:` commit. Options: an `atomic stack-replace` CLI that commits a new file as `Plan: <stack name>` (state `none` only); a general `atomic plan-commit` that commits only `atomic/stack.md` and `atomic/stacks/*` from a reviewed working-tree change (state `none` only, since mid-apply the stack also holds the pop and deferrals); or `stack-move`/`stack-remove` commands built like `stack-add` (from HEAD in a temporary index). Keep the review step: show the exact change and get approval before committing.

## Proposal: Rename `/at:stack` to `/at:propose`, so creating proposals — a new stack, or additions to an existing one — is "propose"
Depends on the `/at:propose` → `/at:spec` rename (done), which freed the name. The command keeps everything `/at:stack` does: elicit a user story, decompose into proposals, write a new stack (refused while a spec is active), or extend the current one via `atomic stack-add`. Reword its intro around "propose work as proposals in the stack". Pipeline becomes `propose → spec → apply → merge`.

Changes: move `.claude/commands/at/stack.md` to `propose.md`; update references in `spec.md`, `apply.md`, `CLAUDE.md` (pipeline, rule 6, Slash Commands table), `README.md`, `.claude/docs/stack-context.md`, and behaviours (rename `pipeline-stack.md` to `pipeline-propose.md`). `Deferred from propose:` now reads naturally for deferrals found during `/at:spec`; decide whether to rename it to `Deferred from spec:`. Also update `package.json`'s description "(propose, apply, merge)", left as is by the `/at:spec` rename because "propose" only becomes the planning command here. The `Plan:` commit prefix stays.

## Proposal: Decide how a repo gets its first `atomic/stack.md` — probably create it when first needed, without being too fussy
Deferred from propose: while specifying `/at:init`, found that nothing creates `atomic/stack.md` until `/at:stack` runs. `atomic stack-add` refuses when the stack is not in HEAD, and `.claude/docs/stack-context.md` says a deferral with no stack should "create it with just the Proposal block", contradicting the mandatory `Stack:` header (also in `pipeline-apply.md` "scope enforcement — stack.md does not exist"). Simplest is likely: whatever first needs a stack (a deferral, `atomic stack-add`, `/at:stack`) creates it with a minimal header such as `# Stack: Backlog`, rather than `atomic init` scaffolding one up front. Decide, then make `stack-add` and the stack rules agree.

## Proposal: Make `bin/atomic` reject unknown flags instead of silently dropping them
Deferred from propose: while specifying consistent `--json` errors, found that the argument loop in `bin/atomic` drops every `-`-prefixed argument other than `--json` (`-*) ;;`). A typo like `--jsno` is ignored, and a positional argument that starts with `-` (e.g. a `stack-add` intent) is lost. Options: error on unknown flags via `die`; support `--` to end flag parsing.

## Proposal: Write the spec to disk before the first human interaction in `/at:spec`, then offer the post-write choices plus "Or tell me what to change"
Deferred from propose: while specifying consistent `--json` errors, the user noted that the spec flow asks for confirmation (step 4 "Summarise back", in practice a **Write** choice) before anything is on disk. Instead, once clarify has enough to go on, write `atomic/spec.md` (and do the stack pop, split-offs, and deferrals) straight away, then hand back with choices like those after a spec is written — e.g. **Apply** — implement this spec now / Or tell me what to change. Changes are edits to the written spec, so the user reviews the real file rather than a summary of it. Overlaps with "Remove the "Summarise back" confirmation step from `/at:spec`" in `atomic/stacks/stack-awareness.md` (move or drop that one when this is done) and with the interaction-pattern proposal (whose candidate list names spec step 4's **Write**). Consider what "tell me what to change" means for the stack: a spec rewritten from scratch may need the pop undone.

## Proposal: Make `/at:spec` write `atomic/spec.md` before popping the stack, so an interrupted spec can't silently skip a proposal
Noticed by the user: step 6 updates the stack "in the same step as writing the spec" but gives no order, and in practice the pop has been written first. If Claude is terminated between the two writes, the state is `none` with the top proposal already gone from the working tree. The next `/at:spec` surfaces the *second* proposal, and the first only survives as an uncommitted diff (recoverable from git, but easy to miss and sweep into an unrelated commit).

Fix: step 5 writes `atomic/spec.md` first; step 6 pops and writes deferrals only after the spec is on disk. The worst interrupted state then becomes "spec exists, proposal still on the stack" — visible (`atomic status` says `proposed`) and recoverable by re-doing the pop. Update the `pipeline-spec.md` scenario "spec written from stack proposal, proposal popped" (today it says "written together") and `stack-context.md` if it implies order.

Option to decide during spec: an `atomic stack-pop` CLI that removes the top block and refuses unless `atomic/spec.md` exists, so the order is enforced by the CLI rather than by prompt wording. It would also make the pop exact (today it is done by hand-editing).

## Proposal: Let stage-end hand-offs offer the next command as a gate verb (e.g. **Spec** — start `/at:spec` now), keeping `Next:` lines for wrong-state exits
Noticed by the user after the interaction pattern shipped: at the end of a stage (merge done, spec written, stack written, init done) the commands end with `Next: /at:<command>`, so the user must type the slash command — unlike `/at:apply`, where **Approve** chains into `/at:merge` itself. Option: make stage-end hand-backs a gate whose verbs run the next command in the same session, with "Or tell me what to change" last; keep `Next:` for wrong-state exits, where nothing should run.

Verbs under current terminology (rename **Plan** with the `/at:stack` → `/at:propose` rename):
- `/at:merge` done → **Spec** — spec the top proposal (`/at:spec`) / **Plan** — design new work as a stack (`/at:stack`)
- `/at:spec` spec written → **Apply** — implement it (`/at:apply`)
- `/at:stack` stack written → **Spec** — spec the top proposal
- `/at:init` done → **Spec** / **Plan**, as after merge

Weigh against context growth: chaining stages in one session accumulates context, which cuts against small models and parallel stacks — consider whether the gate should note "or start it in a fresh session". Update `interaction-context.md` (handoff vs gate definitions), the five commands, their behaviours, and the manifest entry.
